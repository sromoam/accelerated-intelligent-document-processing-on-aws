How We Benchmark Configurations

Section titled “How We Benchmark Configurations”
  • When is agentic extraction worth it?
  • Does holistic classification beat page-by-page classification?
  • Does OCR make a difference?
  • Which extraction model should I use?
  • Can I route review by confidence?
  • What is the cheapest configuration that keeps accuracy?

We answer these questions with benchmark datasets, one page per problem set: Digitization, Splitting and Section Classification, Key Information Extraction, Confidence Assessment and Token Use and Cost.

How we run a benchmark

Section titled “How we run a benchmark”

Most benchmarks start from a baseline setup, change one setting, and run the same documents with each value of that setting. The baseline is the recommended setup above with one difference: its classification reads page images as well as text, because text only came out ahead after the baseline was set (SC-02). A few, such as EX-01 and TU-04, start from each dataset’s own configuration preset instead, and say so. Each benchmark has an ID and a results table; one we haven’t run yet is listed under Planned on its page.

Benchmark Datasets lists each dataset with its preset and its Test Studio test set.

Defaults differ from preset to preset. To configure your own stack, start from the preset closest to your documents.

Why you can trust the results

Section titled “Why you can trust the results”
  • Compare within a question. Each question runs its own documents at its own time, so the same setup can differ by a few dollars per 1,000, or a point of accuracy, from one question to the next.
  • Known answers. Every dataset has ground truth, generated exactly for synthetic documents or checked by people for public ones. See Benchmark Datasets.
  • One change at a time, on one stack, so the setting explains the difference.
  • Same documents, repeated. We run every value on the same documents at least three times and report the spread. The spread is run to run: it shows how much a result moves when the same documents are processed again, not how much it would move on other documents.
  • Real differences only. We name a winner only when the difference exceeds twice its standard error.
  • Pinned to a release. Each table names the release, month and region, and the results file behind it.
  • Tokens, not prices. Tokens stay the same when prices change. Multiply by current prices to estimate cost.
  • Repeatable in your account. Most datasets come with every stack as Test Studio test sets.

Terms

Section titled “Terms”
  • Weighted accuracy: the share of fields right, weighted by each field’s importance, scored with the open-source Stickler library against ground truth.
  • Line-item score: the share of a list’s rows extracted right: matched rows over the larger of the true and returned row counts.
  • Sections exactly right: the share of documents in a packet split at the right pages and given the right class.
  • AUROC: how well confidence separates right values from wrong ones; 50% is a coin flip, 100% is perfect.
  • ECARB (error capture at review budget): if people review the 30% of values with the lowest confidence, how many times as many wrong values they find as a random 30% review would. 1× is no better than random; at 30% the most possible is about 3.3×. See Stickler’s Error Capture at Review Budget.
  • Errors caught reviewing 30% of values: the same review, as the share of wrong values found.
  • Cost per error prevented: the extra cost per 1,000 documents divided by the errors it removes, against the cheapest option. See Marginal Cost of Error.
  • Baseline setup: what most benchmarks change one setting from; see How we run a benchmark.

What the results don’t cover

Section titled “What the results don’t cover”
  • Your documents. Confirm a choice on your own test set; see Measure with ground truth.
  • BDA mode. These benchmarks cover Pipeline mode.
  • Some costs are floors. Costs come from each document’s own metering. Claude Haiku 5.5 bills a prompt over 100,000 tokens at a higher long-context rate; we price that wherever a call’s size can be worked out from the metering, but not for agentic extraction’s calls, and a Lambda attempt that failed and was retried is billed without being metered.
  • Other kinds of documents. Most extraction results come from RealKIE-FCC-Verified, real invoices with checked ground truth. We rely on it because it is accurate and representative of real layouts, but it is one kind of document.
  • Datasets we haven’t built yet: packets with field ground truth, and handwritten forms.
