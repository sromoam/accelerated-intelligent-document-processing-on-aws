Key Information Extraction

Section titled “Key Information Extraction”

What extraction does: turn each section into a database record

Section titled “What extraction does: turn each section into a database record”

Extraction is the step that fills your database. For every section, it reads the pages and returns the values of the fields you defined for the section’s document class. The result is a record: one value per field, in the structure your schema describes.

Two kinds of field make up a record:

  • A field holds one value, such as an invoice’s gross total or a statement’s account number.
  • A list field holds rows, one per item, such as the line items on an invoice or the transactions on a bank statement. Each row has its own fields, such as date, description and amount.

A record’s fields usually become one row in a table for the document class, and each list field becomes a second table with one row per item. In the example below, extraction turns a two-page invoice and a 17-page bank statement into two records:

The invoice has a handful of fields and a short list. The statement has two fields and a list of 800 rows. Both are ordinary documents, and the accelerator offers two ways to extract them, one suited to each.

How the accelerator extracts the fields of a section

Section titled “How the accelerator extracts the fields of a section”

A language model, the extraction model, does the reading. The shipped default is Claude Sonnet 5 (extraction.model). You choose how the model works through the section with Extraction mode (extraction.mode): Simple — single-pass (the default) or Advanced — sharded, for large documents.

What the extraction model reads

Section titled “What the extraction model reads”

In both modes the extraction model receives four things:

  • The section’s text from OCR, every page in order.
  • The page images, so the model can see layout, check boxes and handwriting, and check the OCR text against the page.
  • The fields of the document class, with their descriptions. The accelerator sends each field’s name, type and description to the model. The model treats each description as its instruction for that field, so the description is where you say where a value appears and what format you want.
  • Few-shot examples, if you added any for the document class.

Single-pass extraction (Simple): one request writes the whole record

Section titled “Single-pass extraction (Simple): one request writes the whole record”

In Simple mode the accelerator sends everything above to the extraction model in one request. The model reads the whole section and writes the complete record as JSON: every field, and every row of every list field.

    K --> R[("Record<br/>800 rows")]

A single-pass is the simplest route, and the one that reads the fewest tokens, for a section with a bounded number of fields. Three properties follow from the single request:

  • The model writes every row itself, so the request’s output grows with the length of the list.
  • The whole section has to fit in one request. The accelerator estimates the request size before it sends it, and stops with an explanation (ExtractionInputTooLarge) when the section is larger than the extraction model’s input window.
  • A request with more than 20 page images has each image reduced to at most 2,000 pixels on a side, because Amazon Bedrock caps images at that size in such requests.

See Simple (non-agentic) extraction.

Agentic extraction (Advanced): an agent works through the section in shards

Section titled “Agentic extraction (Advanced): an agent works through the section in shards”

In Advanced mode an agent does the extraction: the extraction model runs in a loop, calling tools the accelerator gives it, until the record is complete and valid. Four mechanisms do most of the work on a long statement.

1. Shards. The accelerator splits the section’s pages into shards: runs of consecutive pages, up to five pages each by default (extraction.agentic.max_pages_per_shard). Each shard gets its own agent, and the agents run at the same time. Every shard after the first also receives the column headings from the first page, so each agent knows what the columns mean. By default the accelerator makes at most 10 shards (extraction.agentic.max_concurrent_batches), so it divides a section of more than 50 pages into 10 shards of similar text length. Each shard runs as its own AWS Lambda invocation under AWS Step Functions (extraction.agentic.runtime: step_functions), so no single function’s time limit applies to a long section, and a retry repeats only the shards that did not finish.

2. The table tool. Before the agents start, the accelerator parses the tables in the OCR text, which Amazon Textract writes as Markdown when its TABLES feature is on (the shipped default). The agent then maps the table’s columns to your row fields (parse_table, then map_table_to_schema), and a third tool (finalize_table_extraction) assembles the rows in code. The model chooses the mapping and never has to write each row out. When the tables parse, the accelerator leaves the page images out of the agent’s prompt (extraction.agentic.table_parsing.lazy_images), and the agent can still open any page with its view_image tool. The table tool is Table Parsing Tool (extraction.agentic.table_parsing.enabled), on in the shipped configuration.

3. A schema check at every step. The agent hands its record to an extraction tool whose input is your schema. The tool checks types, allowed values, patterns and list sizes, and returns any error to the agent, which corrects the record with targeted edits (apply_json_patches) instead of starting again. For a record too large to write in one call, the agent builds it in a scratch buffer, up to 100 rows per edit, and promotes the buffer to the record when it is complete.

4. A merge. When every shard finishes, the accelerator joins the shards’ list rows in page order and takes each single-value field from the first shard that found it.

One more check runs in Advanced mode without any setting: when the OCR text holds a table of more than 30 rows and every list field comes back empty, the accelerator sends the agent back for another try, naming the field and the row count. The agent also scores confidence inside each shard, so confidence scales with the shards; see Confidence Assessment.

What the accelerator checks after either mode

Section titled “What the accelerator checks after either mode”

Every record passes through the same checks before the accelerator stores it:

  • Value coercion (Value Coercion, extraction.coercion) repairs values that do not match their declared type, with no model call: "$1,234.00" in a number field becomes 1234.0, and "03/15/2024" in a date field becomes "2024-03-15". Coercion refuses to guess at an ambiguous value such as 01/02/2024, and records every change. In Simple mode this step runs on the returned record; in Advanced mode the extraction tool’s schema check converts types as values arrive.
  • Schema validation (Schema Validation & Escalation, extraction.validation) checks the record against the full schema, including formats such as dates and email addresses, and records any violation on the section. Validation is on by default and costs nothing.
  • Completeness checks compare each list with what the section’s OCR text shows and raise a processing issue when rows appear to be missing. Short lists and other extraction mistakes describes them.

When one section holds several records of the same document class, such as three pay stubs on consecutive pages, Records per section (x-aws-idp-multi-instance) tells extraction to return a list of records instead of one. See Output Correctness.

Extraction mode applies to every document class in a configuration profile. To process short forms in one mode and long statements in the other, give each its own profile and route each kind of document to it with a prefix mapping.

The configuration to start with

Section titled “The configuration to start with”

For forms and documents with a bounded number of fields, such as invoices, start with single-pass extraction (Simple), the default. One request reads the whole section and returns the record. On real invoices, single-pass extraction scored as high as agentic extraction and read about a tenth of the extraction input tokens (see Invoices).

For documents with long lists, from a few hundred rows up, choose agentic extraction (Advanced). Statements, transaction logs and holdings reports are the typical cases. In our benchmark, agentic extraction returned every row of every statement we tested, up to 3,200 rows on 66 pages, and from 400 rows it finished in about half the time of a single-pass (see Long lists).

In either mode, keep Amazon Textract’s TABLES feature on (the shipped default, ocr.features). The table tool and the row-count checks both read the Markdown tables it produces.

How many tokens extraction uses, and what drives the count

Section titled “How many tokens extraction uses, and what drives the count”

Four things decide how many tokens extraction uses:

  • The rows the model writes. Output tokens grow with the length of the list. In a single pass, Claude Sonnet 5 wrote about 48 output tokens per row of a three-column statement. In agentic mode the table tool assembles the rows, and the agent wrote about 39 per row.
  • How often the model rereads its instructions. A single-pass reads each page once. An agent sends its prompt again on every turn of its loop, and every shard repeats the instructions and the schema, so agentic extraction reads several times the input tokens. Amazon Bedrock serves most of the repeated part from the prompt cache, which it bills at a reduced rate.
  • Page images. Each image adds input tokens, and how many depends on the extraction model and the image size.
  • The extraction model. Models count tokens differently, especially for images, and models differ in how many tokens they spend reasoning.

  • Input tokens per page stayed roughly level as statements grew, in both modes, so a statement’s extraction input scales with its page count and its output with its row count.

How to measure extraction on your own documents

Section titled “How to measure extraction on your own documents”

Ground truth for this step is the correct value of every field and every row in a sample of your documents. Two numbers describe a list field, and a third describes the record as a whole:

NumberQuestion it answers
CompletenessWhat share of the rows in the ground truth came back? Rows returned ÷ rows in the ground truth.
Accuracy over compared cellsOf the values compared in the rows that came back, what share match the ground truth? In our statement benchmark, the compared cells are each returned row’s date and amount, matched exactly.
Weighted accuracyHow close is the whole record to the ground truth, field by field? Stickler scores each field from 0 to 1 with that field’s comparison method, then averages the scores, weighted by each field’s weight.

Read completeness and accuracy together. Accuracy counts only the rows that came back, so a list that returned 43 of 800 rows, all correct, scores 1.0 on accuracy and 0.054 on completeness.

Stickler is the open-source library the accelerator uses to compare results with ground truth. You choose each field’s comparison method: exact for IDs, a tolerance for amounts, date-aware for dates, similarity for names, and item-by-item matching for lists, which pairs each extracted row with its closest row in the ground truth. See Measure with ground truth for the full list and for how the accelerator drafts the ground truth for you, and Weighted Score Calculation for the formula.

Short lists and other extraction mistakes: which configuration makes which

Section titled “Short lists and other extraction mistakes: which configuration makes which”

Once you measure completeness and accuracy, look at what kind of mistake you see. Some mistakes belong to one extraction mode and some to both, and the accelerator reports most of them as a processing issue on the section, which you see in the document list’s Processing Issues column and on the Processing Report tab.

ConfigurationTypical mistakeHow the accelerator reports itWhat to change
Single-pass on a long listReturns the first rows of the list and reports COMPLETEDextraction_rows_below_ocr_estimate (warning)Use agentic extraction
Single-pass on a section too large for one requestStops before extractingThe document fails with ExtractionInputTooLarge, naming the request size and the remedyUse agentic extraction
Single-pass or agentic on a section that holds several records of one classReturns the first record onlyextraction_multi_instance_suspected, when Multi-instance Section Detection is onSet Records per section to Several — wrap my single-record class
Single-pass or agentic with a value in the wrong formatStores the value as the model wrote itextraction_validation_failed (warning)Declare the format on the field, and say it in the description

A short list is the mistake to watch for on long documents. On the 800-row statement, the two single-pass runs that returned part of the list returned its first 43 rows and finished with COMPLETED. They also ran faster and wrote far fewer tokens than the complete runs, so neither the document status nor the run time shows the loss. The accelerator’s row-count check does: it compares the rows extracted with the rows in the section’s OCR tables of the same width, and raises extraction_rows_below_ocr_estimate when fewer than half came back. Across every release 0.6.14 benchmark cell that ran Claude Sonnet 5 in a single-pass on that statement with table-rendering OCR, 9 of 16 runs returned part of the list, and the accelerator raised extraction_rows_below_ocr_estimate on all 9. Source: processing_issue_codes in benchmarks/results/v0.6.14/coresynth__extraction-model-sonnet5/ and astravalue/.

Three settings change what happens to a short list:

  • Make a short list fail the document. Truncated list outcome (extraction.row_shortfall_action) is warn by default: the accelerator records the issue and the document completes. With fail, the accelerator saves the rows it extracted and the issue, then marks the section and the document failed. The check matches tables by column count, so a two-column array that models a group of values, such as an account summary, can borrow evidence from an unrelated two-column table on the same statement. Check your document classes for such arrays before you choose fail; see Making a materially incomplete list fail the section.
  • Declare a minimum list length. Min Items (minItems) on a list field states the fewest rows any real document holds. In single-pass mode a list under the floor raises extraction_list_truncated and a schema violation, and the rows are kept. In agentic mode the extraction tool enforces the floor in every shard, so a floor larger than one shard’s rows fails the section; leave minItems off lists in sections that shard, and use row_shortfall_action instead. See minItems on a list field.
  • Keep the row-count check able to run. The check needs OCR that writes Markdown tables (Amazon Textract with TABLES, or BDA) and a row schema with one field per table column. When the check cannot run on a list of 30 or more rows, the accelerator says so with extraction_row_count_unverified (info).

See Detecting a truncated list for every completeness signal.

What this shows:

  • Wrong values were not the issue on long lists. Missing rows were, which is why completeness is the number to follow.

With Claude Sonnet 4.6 (one run per size, benchmarks/results/v0.6.14/scaling/), a single pass returned every row up to 1,600 rows on 33 pages, taking about 17 and 18 minutes at 1,200 and 1,600 rows, and the 3,200-row statement was too large for one request. Agentic extraction returned every row at every size, in at most about 6 minutes. How long a list a single-pass completes depends on the extraction model.

Improving accuracy once your pipeline is running

Section titled “Improving accuracy once your pipeline is running”

When your test set shows fields with wrong or missing values, these changes help most, roughly in this order.

Write each field description as an instruction. The extraction model reads the description as its instruction for the field. Say where the value appears, what it is not, and the format you want: “Invoice date: the date the invoice was issued, not the due date or the order date, as YYYY-MM-DD.” Edit descriptions in the Document Schema Builder under Description. Most early fixes are wording fixes, and they cost nothing.

Declare types and formats in the schema. Give amounts the type number and dates Format (JSON Schema) date, and use Pattern (regex) or Enum (Allowed Values) for codes. Value coercion then repairs common mismatches for free, and schema validation reports the rest. format: date means ISO 8601 (YYYY-MM-DD); for dates written day-first or month-first, set extraction.coercion.date_order to your documents’ convention. See Value coercion and Schema validation.

Add a few-shot example for a hard document class. A few-shot example is a sample document with its correct values, which the accelerator adds to the extraction prompt for that document class. One or two examples often settle a field the model keeps misreading. Add them under Few-Shot Examples in the schema builder, with the expected values in Extraction Prompt (x-aws-idp-attributes-prompt). See Few-Shot Examples.

Use a different extraction model for one document class. Extraction Model Override (Optional) (x-aws-idp-extraction-model) sets the extraction model for one document class and leaves the rest on extraction.model. Use a stronger model for a difficult class, or a smaller one for a simple class at high volume. See Per-class extraction model override.

Tell the accelerator which pages a field comes from. Some packets leave out optional pages, such as a supplement that only some customers submit. Declare the page types of the document class and, under Source Page Types (Optional) (x-aws-idp-source-page-types), which page type each field comes from. With extraction.missing_field_handling.enabled, the accelerator then marks a field from an absent page as missing instead of blank. See Missing pages vs. blank fields.

Extract every record when one section holds several. When a section can hold several records of one document class, such as consecutive pay stubs or several checks on one page, set Records per section to Several — wrap my single-record class (x-aws-idp-multi-instance: true). The accelerator then returns a list of records, instances, each with its own confidence. Migrate the ground truth of your test sets to the new shape in the same change. To find the sections that need it, turn on Multi-instance Section Detection (extraction.multi_instance_detection.enabled) for a while. See Multi-instance sections.

Let an agent do the tuning. The Auto Optimizer tries changes to descriptions, prompts, models and settings against your test set, within a cost budget you set, and keeps the ones that score better.
